## 1. 总体架构

```
┌─────────────────────────────────────────────────────────────────┐
│                            客户端层                               │
│  家庭用户端(主面板)   陪诊师端   社区商城(内嵌两端)   平台后台(Web)   │
├─────────────────────────────────────────────────────────────────┤
│                            网关层                                 │
│        API Gateway（鉴权 · 家庭域隔离 · 分享码校验 · 限流）          │
├──────────────┬──────────────┬──────────────┬────────────────────┤
│                         业务服务层                                │
│  用户与家庭域   健康档案域    提醒与预警域    陪诊与订单域            │
│  保险域        商城域        医疗资料域      后台运营域              │
├──────────────┴──────────────┴──────────────┴────────────────────┤
│                         智能与集成层                               │
│  AI 服务(LLM)   OCR 服务   通知服务(App/微信/SMS/电话)              │
│  硬件接入网关(华为 Health Kit / 小米运动健康 / 模拟数据源)           │
├─────────────────────────────────────────────────────────────────┤
│                         数据层                                     │
│  主库(PostgreSQL/MySQL)  对象存储(照片/票据/佐证)  缓存(Redis)      │
│  演示版：localStorage + 内存 Mock（见 §8）                          │
└─────────────────────────────────────────────────────────────────┘
```

**四端一后台的归属关系**：社区商城不是独立端，是嵌入家庭端与陪诊师端的公共模块（家庭侧看商城+需求区，陪诊师侧看挂单+需求大厅）；陪诊订单在商城撮合后流转到陪诊与订单域执行。

## 2. 技术选型

| 层 | 演示版（极客松） | 目标版 |
| --- | --- | --- |
| 家庭端 | 微信小程序 / H5（React + Vite），localStorage 持久化 | uni-app 或 Flutter 一码多端 |
| 陪诊师端 | 同一套前端工程，按角色路由渲染（见 §6） | 同左，或独立轻量 H5 |
| 平台后台 | Web 管理台（React + Ant Design） | 同左 |
| 服务端 | 单体 Node.js（NestJS）或 Python（FastAPI），内存/SQLite | 按域拆微服务，K8s 部署 |
| 数据库 | SQLite / 内存 Mock | PostgreSQL + Redis |
| 对象存储 | 本地文件目录 | 腾讯云 COS |
| OCR | 本地 ocr-demo 已验证的方案（PaddleOCR / 云 OCR） | 云 OCR + 人工确认兜底 |
| LLM | 工作台托管的免密钥大模型（glm 系列） | 同左 + 私有化备选 |
| 推送 | 前端轮询/长连接模拟 | 厂商推送 + 微信模板消息 + SMS 网关 + 电话外呼 |
| 硬件 | 模拟数据源脚本（定时写入假心率/跌倒事件） | 华为 Health Kit / 小米运动健康开放平台 |

选型理由：极客松 48h 内，前端优先跑通交互闭环，服务端用单体撑住"多端共享数据 + 角色隔离"两个关键演示点；OCR 复用 `ocr-demo/` 已跑通的管线。

## 3. 业务域与核心数据模型

### 3.1 实体关系总览（ER）

```
Family(家庭) 1──N Member(成员，含老人/子女角色)
Member 1──1 HealthProfile(健康档案：慢病/过敏/用药/手术)
Member 1──N DailyRecord(日常记录：血压/血糖/体重/心率…来源=手动|设备)
Member 1──N Reminder(提醒项目) ──N ReminderLog(闭环记录：已吃药/已查看/代打卡人)
Member 1──N Alert(预警事件：级别/触发规则/处理状态)
Member 1──N Visit(就诊) ──N VisitDoc(就诊资料) ──N MaterialPack(材料包)
MaterialPack N──N InsuranceChannel(社保档案|商业保单) ──N ClaimProgress(报销进度)
Member 1──N ShareCode(分享码：范围/时效/访问日志/撤销)
CareOrder(陪诊订单) N──1 Member(被陪护人)  N──1 Companion(陪诊师)
CareOrder 1──N TaskItem(项目清单项：动作/状态/佐证)
Companion 1──1 CompanionProfile(简介/资质/审核状态) 1──N Availability(可约档期)
DemandPost(需求帖) ──被接单→ CareOrder
AuditLog(操作留痕) ※所有写操作统一落此表
```

### 3.2 关键表字段（演示版最小集）

| 表 | 关键字段 |
| --- | --- |
| member | id, family_id, name, role(elder/adult/admin), avatar, phone, big_mode(大字模式), notify_channels{app,wechat,sms,call}, emergency_contact_id |
| health_profile | member_id, chronic_diseases[], allergies[](强提示), medications[{name,dosage,frequency,stage:长期/近期}], surgeries[] |
| reminder | id, member_id, title, cron_expr, executor_scope(本人/任一家人), channels[], template_key |
| reminder_log | reminder_id, date, status(待办/已完成/已升级), actor_member_id(谁闭环), acted_at, proof_url |
| alert | id, member_id, level(reminder/watch/emergency), rule_key, payload, status(未处理/已处理/误报), created_at |
| visit | id, member_id, hospital, dept, date, status, prep_checklist[], self_description |
| share_code | code, scope(信息卡/任务信息), expires_at, revoked_at, access_logs[] |
| care_order | id, source(mall/demand), member_id, companion_id, hospital, expect_date, help_text, consent_shared(授权勾选), status, next_visit_info |
| task_item | order_id, seq, action, status, proof_urls[], done_at |
| companion | id, name, profile, certs[], audit_status, rating(模拟) |
| availability | companion_id, date, time_slots[] |
| demand_post | id, family_id, hospital, date, help_text, budget?, status(招募中/已接单/服务中/已完成/已取消) |
| insurance_policy | id, member_id, type(社保/商业), company, plan, valid_range |
| material_pack | id, visit_id, docs[] |
| claim_progress | pack_id, policy_id, status(待整理/已提交/待补件/处理中/已办结), history[{status,at,note}] |
| audit_log | id, actor_id, family_id, action, target_type, target_id, detail, at |

## 4. 关键流程设计

### 4.1 预警分级通知（家庭端核心）

```
数据入口(手动/设备/OCR) → 规则引擎评估
  ├─ 提醒级 → 提醒中心落库 → App/微信推送（防打扰：同类 24h 内合并）
  ├─ 关注级 → 落库 → 即时推送 + SMS（全家） → WebSocket 刷新家庭端
  └─ 紧急级 → 落库 → 电话外呼紧急联系人 + SMS + 后台人工介入工单
所有预警必须：可被成员标记"已处理/误报"（留痕）
```

规则引擎首版为纯规则（阈值 + 连续天数），预留 `AlertRule` 配置表，后期可在同接口后挂 LLM 判断"缓慢异常"类。

### 4.2 提醒闭环

```
Reminder 到期 → 按老人账号勾选渠道逐级升级：
  App推送 ──30min 未闭环──▶ 微信/短信 ──2h 未闭环──▶ 电话语音（按键/语音回复闭环）
任一家庭成员可代闭环 → ReminderLog 记录 actor（谁点的）
```

### 4.3 分享码（隐私隔离的关键机制）

```
家庭端选范围(信息卡/本次任务) → 生成 code(10min 有效) → 对方扫码
  → 网关校验 code + scope → 返回 scope 内最小字段集
  → 写访问日志(谁/何时/看了什么范围) → 家庭端可见、可撤销
陪诊师端 API 层面不存在任何医疗档案接口（见 §6），分享码是唯一数据通道。
```

### 4.4 陪诊订单状态机

```
[商城挂单预约 / 需求帖被接单] → 待确认 → 已接单(生成任务清单)
  → 服务中(逐步完成 TaskItem，佐证上传，每步实时同步家庭端)
  → 已完成(生成《陪诊服务单》 + 下次复诊自动转家庭端提醒)
  / 已取消(留痕)
```

### 4.5 OCR 诊疗记录入库

```
拍照/上传 → OCR → 结构化字段(医院/科室/日期/诊断/用药/指标)
  → 人工确认界面（识别值 vs 修正值） → 确认后写入健康档案/就诊资料
未确认数据不入档案（保证档案可信）。
```

## 5. 智能与集成层

| 服务 | 职责 | 说明 |
| --- | --- | --- |
| AI 服务 | 周报总结、健康咨询应答、生成就医准备清单、语音问答 | 统一走 LLM 网关；系统提示词中硬编码"不判读病情、不给诊疗建议"；医疗问题模板化引导就医 |

| 硬件接入网关 | 手表数据抽象层 `HealthDataSource` | 接口：`pullLatest(memberId)`、`subscribeEvents(memberId)`；实现类：华为 / 小米 / MockSource（极客松用 Mock） |

## 6. 权限与隐私架构（红线实现）

三层防线：

1. **接口层（RBAC + 数据域）**：所有 API 按 `家庭域(family_id)` 隔离；陪诊师角色 token 在网关层就不携带任何 `/health-profiles/**`、`/visits/**` 路由的权限——不是"前端不显示"，是服务端无此接口权限。
2. **数据层（分享码）**：跨域（家庭→陪诊师）只有分享码一条通道，短时效、可撤销、留痕。
3. **审计层**：家庭内写操作统一过 `AuditLog` 中间件；分享码访问单独留痕。

家庭内"无隐私默认"：成年成员对同 family 全部健康数据具备读权限（数据库层面即如此，不做逐条授权开关）；仅"紧急联系人"等敏感字段保持单点维护。

## 7. API 设计（REST 资源一览）

```
POST /auth/login                        # 手机号+验证码（演示：直接选角色登录）
GET  /families/{fid}/members
GET  /members/{mid}/health-profile      # 家庭域内
POST /members/{mid}/daily-records
GET  /members/{mid}/trend?range=week|month
GET  /members/{mid}/reminders   POST /reminders  POST /reminders/{id}/close
GET  /alerts    POST /alerts/{id}/ack
POST /visits    POST /visits/{id}/prep-checklist  POST /visits/{id}/docs(OCR)
POST /share-codes   DELETE /share-codes/{code}    GET /share-codes/{code}/content  # 扫码侧
GET  /insurance/policies    POST /material-packs   POST /claims/{pack,policy}/progress
POST /companion/orders   POST /orders/{id}/tasks/{seq}/done(附佐证)
GET  /mall/companions   GET /mall/companions/{id}/availability
POST /demand-posts   POST /demand-posts/{id}/accept
POST /admin/audits   POST /admin/interventions            # 后台
```

约定：家庭域接口统一带 `family_id` 校验；写接口自动落 AuditLog；陪诊师 token 请求任何 `/members/*/health-profile` 返回 403。

## 8. 部署与演示方案

- **演示版（极客松现场）**：单机跑通——前端 H5 + `npm run mock`（内存数据服务，提供 §7 全部接口 + 预置模拟数据：王阿姨一家、陪诊师 2 名、模拟手表数据流）。保险模块按需求走 localStorage。预警/通知用前端弹窗 + 声音模拟电话。
- **目标版**：Docker Compose（网关 + 单体服务 + PG + Redis + MinIO）起步，量起来后按域拆分。
- 环境要求：演示机离线可用（Mock 数据内置），避免现场网络翻车。

## 9. 代码仓库与协作规范

### 9.1 仓库策略

- **实际仓库**：`fanyuxilin-ai/kangban-family-care`（GitHub 公开仓库，仅三人协作）为本期唯一开发主线；成员私人仓库仅备份原有代码，不再提交。
- **本期形态**：单页静态原型（`index.html` + `app.js` + `styles.css`，localStorage/IndexedDB 本机存储），无构建工具；改动按模块提交到独立分支，全部逻辑集中在 `app.js`，**必须走分支 + PR 避免覆盖**（见 §9.2）。
- **演进目标（本期不做）**：比赛后若继续演进，再迁移到 monorepo：

```
kangban-app/
├── apps/
│   ├── family/          # 家庭端（成员A、B）
│   ├── companion/       # 陪诊师端（成员C）
│   ├── mall/            # 社区商城公共模块（成员C）
│   └── admin/           # 平台后台
├── packages/
│   ├── shared-ui/       # 公共组件（按钮/卡片/状态标签/大字模式）
│   ├── api-client/      # 接口封装与 Mock
│   └── design-tokens/   # 设计变量（见设计文档）
├── services/            # 服务端（单体，按域分 module 目录）
├── docs/                # 本三份文档所在
└── mock/                # 模拟数据与模拟设备源
```

### 9.2 分支与合并

- `main` 可演示（随时能跑）；开发在 `feat/<模块>-<功能>` 分支；合并走 PR + 一人 review（维护者操作 merge）。
- **模块化开发**：本期代码集中在 `app.js` 单文件，约定**按功能区块注释分区**（如 `/* 健康预警 */`、`/* 陪诊履约 */`），各自只在本人负责的区块内改代码；改动前先 `git pull origin main` 同步，跨区块修改在 PR 里单独说明，方便 review。
- 文档同样模块化：三份文档放 `docs/`，各成员在自己的小节创作，文档改动单独分支提交，定期由负责人合入，避免互相覆盖。

## 10. 风险与技术对策

| 风险 | 对策 |
